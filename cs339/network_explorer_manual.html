01 · FIRST STEPS

Start with a working network

Network Explorer is a simulated network lab. Build a topology, configure its devices, send traffic, and inspect the decisions along the path. Everything happens inside the model; the Browser application does not browse the real Internet.

  1. From Home → Example networks → Basic, open Simple LAN.
  2. Select one host. The Inspector shows its configuration; the Terminal lets you issue commands.
  3. Select the other host and note its IPv4 address. Switch back to your source host and enter ping followed by that address.
  4. Watch frames travel through the switch. Open Activity and select a row to read the frame and event details.
  5. Turn on Watch for the switch, then repeat the ping. Read each explanation and choose Continue.
Make the first exchange visible. ARP and MAC learning change what happens on subsequent attempts. Use Clear learned state before repeating a cold-start experiment.

04 · BUILDING BLOCKS

Place and configure devices

Choose a device in the palette, then click a clear spot on the canvas. Press Esc to cancel placement. Select a device to open its Inspector; drag it to reposition it.

Host

An endpoint that sends and receives traffic. Set its name, operating system, static IPv4 address and prefix, default gateway, and DNS server, or choose DHCP. Hosts can run server and browser applications.

Switch

Connects Ethernet interfaces inside a LAN. Configure its access VLANs and port state. Inspect the MAC forwarding table to see which source MAC was learned on which port.

Router

Connects IP subnets. Each routed interface has its own address and prefix. Inspect connected and static routes, ARP entries, DHCP relay settings, NAT/PAT, and optional firewall policy.

Firewall

A transparent two-port appliance with stateful filtering enabled. It bridges frames without IP addresses, routing or NAT. Configure zones, rules and sessions in the compact Firewall section.

Addressing checklist

  • Give each host a unique address in its intended subnet. The prefix determines which destinations it considers local.
  • For remote destinations, set the host gateway to the router interface on the same LAN.
  • Configure a reachable DNS server when using hostnames.
  • On routers, address both sides of the path and provide routes for the return journey.

Use the linked CIDR Teaching Tool beside host addressing when you need to work through subnet calculations. Device OS/platform selections change the terminal command vocabulary; they do not provide a complete operating system.

To configure a host address, click its eth0 port in Interfaces. Choose Static or Automatic (DHCP) in the port editor; Static exposes the IPv4 address and prefix, with the CIDR Teaching Tool link beside the address. DHCP acquisition, renewal and lease status are also in this editor. Default gateway and DNS server remain at host level and can be supplied by DHCP. To remove a statically assigned host address, empty the IPv4 address field and press Enter or leave the field. The host returns to Not configured; its prefix and gateway are cleared. DNS settings and applications remain. A configured DHCP server needs a static address, so remove its server configuration before clearing that address. The Terminal also supports the OS-specific address commands below.

05 · CONNECT THE NETWORK

Cables connect interfaces

  1. Use a device’s connection anchor to start a cable. Drag to the other device’s anchor, or click the two endpoints.
  2. Choose an available Ethernet interface when the port picker appears. An In use port already belongs to a cable.
  3. Complete the other end, then check the connection and interface state.
  4. Select a cable or interface to inspect it. Enable or disable the connection/interface to experiment with link failures.

You can also drag a device onto another device to begin a connection. An anchor may be reused for several cables, but each cable needs available interfaces. Move the devices to improve wire routing.

Link up does not mean IP reachable. Link indicators show connection/activity state. A lit link can still have an incorrect VLAN, IP address, gateway, route, or missing application.

The model blocks Layer 2 loops. Build loop-free switched LANs; routed links can form different paths when their routes are configured.

07 · UNDERSTAND THE LAN

Ethernet, ARP, and VLANs

A host needs a destination MAC address before it can deliver an Ethernet frame. ARP resolves an IPv4 address to a MAC address on the local LAN. For a remote IP destination, the host resolves its gateway’s MAC.

A switch learns the source MAC on the incoming port. It forwards a known destination toward the learned port, and floods broadcasts or unknown destinations to eligible ports in the same VLAN.

Separate traffic with access VLANs

  1. Select the switch and create/name the VLANs you need.
  2. Select each interface and assign its access VLAN. VLAN 1 is the default.
  3. Send traffic between hosts in the same VLAN, then compare with hosts in different VLANs.
  4. Inspect the forwarding table and Activity VLAN column to explain the result.

Access frames are untagged. This workflow models access VLANs, not trunk links carrying tagged traffic. A router connects IP subnets; a switch alone does not route between VLANs.

Find and copy a MAC address

Select a device, then click its interface. Every port dialog shows the interface MAC below Connected to, with a copy SVG. Use the interface facing the relevant LAN when a router has multiple interfaces. In an ARP Inspection binding MAC field, type $ to select that address directly. The $ picker is supported in this field and Terminal; @ continues to insert IP addresses or hostnames in its supported fields.

Read the tables

The MAC table maps MAC addresses to switch ports and VLANs; the ARP table maps local next-hop IP addresses to MAC addresses. Table highlights help relate entries to the topology. Use Expand table to keep a table visible in a movable panel and Dock to return it. Expiration indicators help explain why an entry disappears or is relearned.

08 · CROSS A SUBNET BOUNDARY

Routing and NAT/PAT

Routers select the matching route with the longest prefix. Connected routes come from interface configuration. Static routes specify how to reach remote networks. Hover over a routing-table entry, or focus it with the keyboard, to highlight the cable attached to its outgoing interface.

Configure a routed path

  1. Give each router interface an address/prefix for its attached subnet and enable it.
  2. Set each host’s default gateway to its local router interface.
  3. In the router’s routing table, choose Add static route. Enter a name, destination network, prefix, and next hop; save it.
  4. Add the corresponding return route where needed. Inspect routes and use ping/traceroute to test both directions.

At each routed hop, the Ethernet header changes and TTL decreases. The source and destination IP addresses normally remain the same; NAT is a deliberate exception. No matching route or an expired TTL can produce an ICMP error.

Share an outside address with NAT/PAT

  1. Open Internet and NAT for a configured example, or select your own router.
  2. In NAT / PAT, enable outbound NAT. Open the settings for each relevant interface and set its NAT role to Inside or Outside / WAN.
  3. Ensure addressing, gateways, and routes work on both sides. Generate client traffic toward the outside network.
  4. Inspect the NAT table and Watch explanations for the inside address, translated outside address, and port/identifier mapping.
Read both directions. Outbound translation creates runtime mappings; return traffic uses them to reach the private client. NAT/PAT changes addresses; the separate Firewall panel controls which routed conversations may pass. Inbound port forwarding is not modeled.

Nmap port scanning

Drag Nmap from the palette's Tools section onto a configured Windows, Linux, or macOS host. You can also place it on the canvas and connect it to a host, just like other applications.

  1. Select the installed Nmap application.
  2. Choose the Terminal pill to paste nmap -sS -p 22,80,443 with no target address.
  3. Type @ and choose a target IP, or type the address yourself, then press Enter. Use the normal playback controls to pause, step, or finish the exchange.
  4. Read results in Terminal and inspect TCP probes in Activity.

Open means a SYN-ACK arrived; closed means a reset arrived. Filtered means no response before the simulated timeout; an unavailable host or broken path can produce the same result. An open port does not identify the service or verify a TLS certificate.

This teaching subset supports one IPv4 target and up to 16 comma-separated TCP ports, one SYN probe per port, without host discovery, retries, UDP scanning, or service detection. Run Nmap commands in the host Terminal after installing the tool. Enter nmap or nmap --help for usage. Installation and the last command persist in saved networks; runtime scan results clear on reset.

09 · DECIDE WHAT MAY PASS

Stateful firewall policy

Firewall and NAT / PAT controls appear below Interfaces and above the routing table on routed devices. When either feature is disabled, only its heading and enable toggle remain visible; enabling it reveals its settings or runtime details.

Place Firewall from the device palette, or enable Firewall in an existing router’s Inspector. The dedicated device is a two-port transparent bridge with filtering enabled, Inside and Outside zones, an outbound allow rule, and default drop. Insert it inline between a switch and router, or between two hosts on the same subnet. It needs no IP address, routing table, or NAT, and preserves frame addresses and IP TTL. Existing routers retain optional routed filtering, disabled until you enable it. Older saved routed firewall devices retain their routed behavior.

  1. For a dedicated transparent firewall, connect its two bridge ports into the traffic path; leave host IP addresses and gateways unchanged. For a router with filtering enabled, address its routed interfaces and configure gateways and routes. Both directions of a conversation must cross the filtering device.
  2. Assign each interface a security zone: Inside, Outside, or DMZ. These are independent of NAT roles. A three-interface router can represent all three zones.
  3. Choose Add rule. Name it; select from/to zones, source and destination IPv4 addresses or CIDR networks, protocol, optional source/destination ports, and allow/drop. Use * for any address or port. Ports require TCP or UDP.
  4. Save the rule. New rules appear last. Use the up/down arrows to set priority; the first enabled matching rule handles a new conversation. Edit, disable, or delete a rule using its row controls.
  5. Set If no rule matches to drop or allow. A tracked reply uses the permitted session rather than needing a new reverse-direction rule.

Sessions shows permitted conversations and states; Recent decisions shows the last 12 allows/drops. Idle sessions expire after 120 seconds. TCP requires a SYN, matching SYN-ACK and ACK; FIN/ACK or a valid reset closes the session. UDP uses endpoint/port matching; ICMP echo replies must match the request identity.

Placement matters. Only traffic that crosses the device is filtered. A transparent firewall can filter same-subnet traffic when placed between the hosts. Hosts connected to the same switch on one side bypass it. A router firewall filters traffic routed between its interfaces.

Try the Firewall example

  1. Open Home → Advanced → Firewall. Open Inside Client’s Browser and browse to http://www.firewall.example/. DNS and HTTP pass, including stateful replies.
  2. From Inside Client, run ping 198.51.100.10. Default drop stops this new ICMP exchange. Watch Edge Firewall to see the rule decision; the client times out.
  3. Open Outside Services’ Browser at http://192.168.10.20/. The unsolicited inbound connection is blocked.
  4. From Inside Client, ping 192.168.10.20. This same-subnet exchange bypasses the firewall and succeeds.
  5. In Incidents, choose New incident, select Firewall, and start an incident. Investigate the failing service and ordered policy rules, then use Check repair.

Watch the decision and NAT ordering

Enable Watch on the firewall and send traffic. Examine identifies allow/drop, the rule, security zones, protocol and session state. A dropped packet has no outgoing frame; the sender receives no explicit rejection. Activity records the decision. On routers, policy evaluates after inbound reverse NAT and route selection, before outbound NAT, so rules use the internal client address. Transparent firewalls bridge allowed frames unchanged and perform no NAT. Examine shows original and translated headers when NAT applies.

Scope of this teaching model

This is an IPv4 traffic policy model. Transparent firewalls pass ARP and DHCP unchanged, even with default drop, so discovery and address configuration work across the bridge. Router filtering excludes ARP, locally addressed traffic, and DHCP relay control traffic. It supports the simulator’s ordered TCP exchanges, UDP and ICMP echo; related ICMP errors through the firewall, TCP retransmission, host firewalls, VLAN trunks, application/content inspection, VPNs, and port forwarding are not modeled. Firewall settings are configured in the Inspector; routers retain router commands; transparent devices expose bridge-port status. Configuration edits clear learned state so the next test uses the new policy. Save/load preserves rules and zones, not live sessions, counters, or decision history.

Firewall CLI inspection

Select the firewall or router and use its Terminal. Help and Tab completion follow the selected operating system. Operational commands show the same policy, sessions and recent decisions as the Inspector. On PAN-OS, operational inspection uses committed policy; exit configuration mode first. Continue using the compact Inspector for rule edits.

10 · GIVE HOSTS A SERVICE

Applications and DHCP

Choose DHCP server, DNS server, Web Server, or Browser from the palette. Click a host to install it, or place it on the canvas. Select the application icon to configure it. Application icons belong to their hosts; they do not need separate Ethernet cables.

Supply client configuration with DHCP

  1. Give the server host a suitable static IP address.
  2. Install and enable the DHCP server application.
  3. Create a pool: name, start/end addresses, prefix, gateway, DNS server, and lease duration. Keep the pool appropriate for the client subnet.
  4. Set the client to DHCP and acquire a lease using its Inspector control or OS-specific renew command.
  5. Inspect the client’s assigned address, gateway, DNS settings, lease timer, and server leases.

A lease has a lifetime. Its countdown uses real time; renew it to extend the lease. Activity lets you follow discovery, offer, request, and acknowledgment.

Reach a DHCP server on another subnet

Use the DHCP relay example. Configure a helper/server address on the router interface facing the client LAN. The remote server needs a pool for that client subnet, and routers need routes in both directions. A local broadcast by itself does not cross a router.

Check configuration before connectivity. If a client cannot obtain an address, investigate the pool, application state, link/VLAN, and relay first. Do not begin by assuming DNS is the problem.

11 · FROM A NAME TO A PAGE

DNS and web browsing

Resolve a hostname

  1. Install and enable DNS on a reachable host.
  2. Add an A record containing a name, IPv4 address, and TTL; save it.
  3. Set the client’s DNS server address, directly or through DHCP.
  4. Run nslookup server.example using your actual record name. Inspect the response, cache, and Activity.

A cached answer can avoid a new lookup until it expires. Flush the client DNS cache when testing a record change or repeating a first lookup.

Serve and fetch a page

  1. Install Web Server on a host. Enable it, configure its port and HTML response, including any title and heading markup. Valid changes apply automatically.
  2. Install Browser on a client. Enter an http:// URL using the server address or configured DNS name, and choose Go.
  3. Follow DNS (if required), TCP setup, HTTP GET, and the response in Activity.
  4. Use Reload to repeat the request or Expand to enlarge the browser view.
Use the modeled web service. The server serves one small page at / and /index.html, up to 8000 UTF-8 bytes in the configured page body. Browser renders supported HTML text, headings, lists, tables, and formatting; scripts and external resources are not executed or loaded. Use HTTP, or HTTPS with a configured certificate. This is an instructional TCP/HTTP exchange, not a general web browser or full TCP performance simulator.

13 · FOLLOW THE DECISIONS

Animation, Watch, and Examine

Choose Slow, Normal, Fast, or Turbo for the animation pace. Choose Immediate to complete every exchange without packet animations or Watch pauses. All engine events are still processed: Activity, command results, learned tables, leases, caches, NAT mappings, and application results update normally. Selecting Immediate during an exchange finishes the remaining traffic immediately; Watch settings remain available when you return to an animated speed. Pause/resume lets you stop movement; Finish current exchange immediately advances the exchange without waiting through the animation.

  1. Select a device and open its eye-shaped Watch dropdown. Choose Off, All, or check the decision types you want to examine. Choices depend on the device; applications offer Off and All for their own activity.
  2. Generate traffic. A watched decision opens Examine and pauses the exchange.
  3. Read the incoming evidence, header values, tables, and explanation of the selected action.
  4. Choose Continue to proceed. Disable Watch in the dialog or on the device when you no longer want these stops.

Canvas shortcuts: Double-click a device to open and focus its terminal. Double-click an installed application to open its host terminal while keeping the application selected. Ctrl-click a device or installed application to select it, enable Watch, and open the Watch options dropdown. Existing decision choices are retained.

To focus on routing, select the router, choose Off, then check Routing / longest-prefix match. ARP still runs, but its separate exchanges do not interrupt you. A routing explanation can still show an outgoing ARP request when the chosen next hop needs resolution. Watch choices are independent of traffic filters and are included when you save the network.

Expand Examine when you need more room. Compare the incoming frame with the outgoing decision: flooding versus forwarding, next-hop ARP, route selection, TTL changes, or NAT translation, or firewall allow/drop.

Watch and monitoring answer different questions. Watch pauses at a decision. Activity monitoring selects which devices contribute visible capture evidence. A display filter narrows what you see; it is not a network firewall.

Simulation ticks and animation speeds are teaching aids, not measured network latency or bandwidth.

17 · INVESTIGATE, REPAIR, VERIFY

Practice with incidents

The Incidents tab is your workspace for investigating a hidden fault and checking your repair.

  1. Choose New incident to open the chooser. Browse Featured practice areas, search, or filter by Connectivity/Security and area difficulty.
  2. Select Use current network to introduce a fault in your topology, or Load practice network for a prepared network. Generated practice networks require a separate Network complexity choice: Basic, Intermediate, or Advanced. This controls network size and layout independently of area difficulty; a Basic interface incident can run on an Advanced network. The chooser checks compatibility when you select an area. If the current network cannot support it, Load practice network is selected automatically and Use current network is disabled. An inline notice explains the replacement; starting still asks before replacing an existing network.
  3. Choose a practice area, or use Randomize to choose within the visible results. Areas include Interfaces, Routing, VLANs, DNS, DHCP, Web services, ARP spoofing, Firewall, and Wi-Fi authentication.
  4. Expand Settings to optionally enable @ links, which makes device names in the report clickable, or Starter to include a suggested first command or Browser action in the report. Starter is off by default. Choose Get to work!. A randomly selected applicable fault is verified against a working baseline. The chooser closes and the incident symptom appears in the tab.
  5. Investigate using the Terminal, Activity, caches, and Inspector. Use Hint for progressive guidance, Look here to locate a relevant device, and Reveal fault if needed.
  6. Repair the network and choose Check repair. A fresh test avoids cached state; ARP incidents check attack resistance as well as HTTP connectivity. Explain your evidence and fix when the test passes.
  7. Reset network restores the saved working baseline, discards incident edits, and lets you start another incident.
Focused practice, varied faults. Selecting an area keeps the challenge on that topic without revealing the fault. When alternatives are available, the next incident avoids the previous fault. If your current network has no verified incident in that area, choose a practice network. No fault is applied when validation fails.

Compare HTTP with HTTPS

  1. Open Web browsing and load the HTTP page. Select an HTTP response in Activity to read its headers and body.
  2. Choose Certificate in the palette, then click the Web Server application or its host. This attaches a simulated certificate, enables HTTPS, and changes the default port from 80 to 443.
  3. In the Web Server inspector, check the certificate hostname. It must match the Browser URL hostname (or IP address). The issuer must be trusted and the certificate within its validity period. Valid Web Server changes apply automatically.
  4. Open Browser and change the address to https://server.example/, using your server's name and configured port.
  5. Filter Activity with tls. The simplified handshake checks identity before sending encrypted application records. The Browser displays the decrypted page; captured records hide the HTTP path, headers, status and body. IP addresses, TCP ports, sizes, and timing remain visible.
  6. Try an incorrect certificate name, an untrusted issuer, or an invalid validity period and repeat the request. The page is blocked before HTTP content is sent.

Each Web Server listens on one configured port using HTTP or HTTPS. Switch transport in its inspector to compare them. Removing its certificate returns it to HTTP. A certificate identifies the server; shared traffic keys protect the content. This is a teaching simulation, not real cryptography or a complete TLS implementation. Certificate fields in the simplified handshake are teaching annotations, not a TLS 1.3 wire decode. Ordinary DNS queries remain visible.

DoS: keep HTTPS available

Open the Security example of this name. Its external Traffic Generator sends a bounded burst of TCP SYNs and deliberately ignores replies. The protected Web Server has eight pending-handshake slots and a 120-tick timeout. The external and protected segments use a transparent firewall and share an IP subnet.

  1. Load the Legitimate Client HTTPS page to verify the baseline.
  2. Open Traffic Generator, choose Legitimate Client under Availability check, and Run burst. The optional check requests that client's numeric-IP Browser URL midway through the burst.
  3. Use canvas Pause and Step to inspect the exchange. A temporary canvas capacity monitor shows occupied slots, dropped SYNs, and expired handshakes. Activity shows actual simulated packets and capacity drops.
  4. Finish the exchange, then reload Browser to verify recovery after pending slots expire.
  5. Add a firewall DROP rule for the load source, above the public HTTPS allow rule, and repeat. Legitimate access should survive.

Traffic Generator is installable on hosts from Tools. Each run is limited to 100 SYNs. Choose Slow, Medium, or Fast to control the interval between attempts. Stop cancels future sends; in-flight packets and pending connections still expire normally. The capacity monitor initially appears on the canvas and shows live usage. Drag its handle to reposition it; its connector uses the nearest card edge and host anchor. Use the close SVG to move it to the top of that host's Inspector, expanded. The restore SVG returns it to the canvas. Its 60-second idle countdown continues in either view; pending connections keep it active, and new activity refreshes the countdown. After expiry, a new activity period starts on the canvas. Capacity and timeout come from the network configuration; the DoS example supplies its own limits. This first model covers single-source connection exhaustion, not bandwidth saturation or distributed attacks. The existing IDS/IPS port-scan detector counts distinct ports; it is not a flood detector.

Security hardening examples

Open the Security accordion on Home. Four exercises begin with working, intentionally insecure networks: Secure HTTP with HTTPS, Reduce exposed services, Detect a port scan, and Detect versus Prevent. Read the canvas walkthrough note for baseline commands, configuration steps, and success checks. Browser and Nmap are already installed where needed. Reload the same example to restore its starting configuration.

These are hardening exercises: keep the required HTTPS service working while improving confidentiality, access control, detection, or prevention. They do not start with a broken connection.

Firewall and IDS/IPS monitoring

Select the device to enable the firewall, edit zones and rules, and choose intrusion mode: Off, Detect, or Prevent. Detect reports possible port scans without changing the policy decision. Prevent drops new SYN probes once the configured number of distinct destination ports is observed from one source to one destination within the tick window. Repeated probes to the same port count once. Only SYN headers are inspected; TLS content stays encrypted.

Firewall devices automatically have two attached monitoring applications. Ordinary routers show only the Firewall monitor when their firewall is enabled; IDS/IPS is available only on dedicated Firewall devices. Select Firewall to view active sessions and recent policy decisions. Select IDS/IPS to view intrusion alerts, observed ports, and the resulting action. Use an alert's Activity link to examine the triggering packet, or the device link to return to configuration. These built-in monitors require no installation.

ARP Spoofer app

The ARP Spoofer claims that another IPv4 address belongs to its host's MAC address. The victim and impersonated peer must be reachable on the attacker's local VLAN. Only simulated packets are sent.

Run a comparison

  1. Open Home → Security → ARP: protected LAN for the protected example. For an ARP incident, open Incidents → New incident, select ARP spoofing, and choose the current or a prepared practice network. For a custom network, install ARP Spoofer from the palette's Tools on the attacker host.
  2. Open the victim's Browser and load its page before attacking. You can also test from the victim's Terminal. The attacker does not test the victim's connection for you.
  3. Open ARP Spoofer ? Settings. Set Victim IPv4 and Impersonated IPv4 (usually the gateway); type @ to choose an address. Choose Forged request or Forged reply, Poison victim only or Poison both endpoints, and Drop or Forward intercepted traffic.
  4. Set Rounds and Speed. One round is enough to demonstrate a false claim. Repeated rounds reassert it if legitimate ARP traffic changes a cache. Slow, Medium, and Fast set the interval between rounds in simulation ticks; canvas playback speed is separate.
  5. Use the play SVG (Run attack). The app first discovers real endpoint MACs with ordinary ARP, then sends forged claims. Its running indicator shows Poisoning; Rounds complete means sending has finished, not that poisoned caches or forwarding have ended.
  6. Generate fresh traffic from the victim. Drop mode interrupts delivery; Forward mode can keep the page working while the attacker observes traffic. Compare the victim's result with the attack status and packet count.

Read Interception

The Interception tab shows the latest 100 captured packets, newest first. The list fills the available pane height and scrolls above the uninstall footer. Rows identify the protocol, endpoints, and Forwarded or Dropped action. Expand View payload for readable application data such as an HTTP request or response. TCP acknowledgments can have no application payload. HTTPS/TLS records show Encrypted content; IP addresses and transport metadata remain visible.

Use Watch and canvas Pause/Step to follow individual decisions, and Activity to inspect the packet history. Watch's ARP category covers ARP processing; select the relevant TCP or other decision categories when investigating later traffic. ARP sender/target MACs are separate from Ethernet source/destination addresses.

Stop poisoning cancels future forged sends. In-flight packets, poisoned caches, and attacker forwarding can remain. Clear learned state ends interception and clears runtime caches and security logs while preserving configuration. Save/load stores app settings and inspection policy, not poisoned caches, queued attacks, or captured content.

For an HTTPS comparison, attach a certificate to the Web Server, use a matching HTTPS URL in the victim Browser, and rerun the attack after service configuration changes reset runtime. Forwarded HTTPS can still work, but its HTTP content is hidden from the attacker.

This teaching model learns targeted ARP requests and unsolicited replies; gratuitous ARP learning is not modeled. Relaying changes Ethernet delivery while preserving IP endpoints, TTL, and TCP state.

Protect a VLAN with ARP Inspection

On a switch, open VLANs and enable the ARP Inspection toggle on a VLAN card. An ARP Inspection app appears beside the switch while at least one VLAN is inspected. Disabling the last inspected VLAN hides the app. VLAN inspection toggles remain on the switch; the app displays inspected VLANs as read-only colored badges.

Settings: trust and approved bindings

The Settings tab shows the switch's ports, link indicators, VLAN colors, and trust toggles. Untrusted means ARP claims must pass inspection; it does not mean the port is disconnected. Trusted ports bypass inspection. Leave endpoint ports, especially the attacker port, untrusted. Ports in VLANs that are not inspected are dimmed and their trust controls are disabled.

  1. Under Bindings, choose the plus SVG to open the add form.
  2. Enter the legitimate sender's IPv4 address, or type @ to select it.
  3. Enter its MAC, or type $ and choose the correct device interface. A router has a different MAC on each interface. You can also open a port dialog and use the copy SVG beside its MAC address.
  4. Choose the VLAN and Ingress port: the port on this switch through which that sender's ARP enters. For the gateway, this is the switch port connected toward the router, not the router's interface name. The open port dropdown shows VLAN, inspection/trust status, and connected device. Ports outside the selected VLAN cannot be selected.
  5. Use the save SVG at the bottom right, or the cancel SVG to discard the form. Saved rows show IPv4, MAC, switch port, and VLAN; use the trash SVG to remove a binding.

Include each legitimate sender on inspected, untrusted ports. In the protected example, the attacker also has a legitimate binding for its own address; that does not authorize it to claim the gateway's IP. This is a static IP/MAC/VLAN/ingress-port model, not DHCP snooping. Inspection checks the Ethernet source against the ARP sender MAC and validates the approved binding. Settings apply immediately on both switch profiles.

Decisions and recovery

Open Decisions to review allow/drop results. Inspection blocks new false claims but does not repair a previously poisoned cache. Select each affected host or router and use the eraser SVG in the ARP cache header (Clear this ARP cache), beside Expand table. Then generate fresh traffic. Clearing one cache preserves the rest of the network state.

Protected LAN exercise: verify that the victim page works and forged claims are dropped. Trust attacker port P2, rerun the attack, and test again. Inspect the switch decision, then repair by removing trust from P2. Clear learned state to start a fresh comparison, rerun the attack, and reload the victim page. Success means the page works, false claims are dropped, and the new attack captures no packets. Reload the example to restore its starting configuration.

Join a wireless LAN

Open Wireless LAN under Home → Intermediate. The laptop starts associated with Classroom and has a DHCP address. Ping 192.168.50.10 to reach the wired server. The AP bridges frames between Wi-Fi and its Ethernet uplink; it does not route or supply DHCP.

  1. For your own network, place a Wireless access point and Wireless laptop from the palette. Cable the AP's Ethernet interface to a switch or router.
  2. Select the AP to set its SSID, Open or WPA2-Personal security, and password.
  3. Select the laptop, choose the network, enter its password, and click Connect Wi-Fi. Activity records authentication and association. Dashed links represent wireless associations.
  4. After association, choose Automatic (DHCP) and acquire a lease, or configure a static address. Then test connectivity. Disconnect removes the association and clears a DHCP address.

The model supports seven clients per AP. Saved topologies preserve SSIDs, simulated passwords, and connection profiles; DHCP leases and captures are runtime state. WPA2 is an admission check, not a cryptographic implementation. Signal range, interference, roaming, WPA3, and enterprise authentication are outside this model. Use classroom-only passwords.

Network Explorer · CS339 · User Manual

Learn routes with OSPF

Open OSPF: three-router network from Examples. Routers exchange messages, learn their own link-state databases, and calculate lowest-cost paths. No router reads a global topology to discover routes.

The example starts with all links enabled and valid OSPF configuration. For an optional troubleshooting exercise, open Incidents and choose Dynamic routing. The simulator chooses one verified fault; investigate neighbors and route costs, use progressive hints, and check your repair.

Configure a router

In the Router Inspector, enable OSPF. Click an addressed port to set its OSPF participation and cost: Active discovers a directly cabled router; Passive advertises a host LAN without Hellos; Off excludes the interface from OSPF. Port OSPF controls appear only while router OSPF is enabled; choosing Off hides the cost setting. Each router needs a unique router ID. Area is fixed at 0. Costs default to 1 and are summed along the path, including the destination LAN. Advanced Hello/dead intervals must match at both ends; defaults are 10/40 simulation ticks.

Observe discovery and convergence

Use the OSPF neighbors and LS DB tabs beneath the configuration. Each database entry shows its advertising router, sequence, age, neighbor links, and advertised networks with their costs. Hellos establish bidirectional communication, database descriptions identify missing advertisements, requests and updates synchronize the databases, and acknowledgments stop retransmission. Full means database synchronization is complete. Router-LSAs carry sequence numbers and age; newer advertisements replace older ones. The routing table labels learned entries OSPF and shows their cost. Static routes win for identical prefixes; longest-prefix matching still applies.

Use the existing canvas Pause/Run control and Step button. Pause freezes protocol time; Step advances one event, or one idle tick when nothing is pending. Fast-forward processes a bounded burst. Immediate mode removes animation without bypassing protocol decisions. OSPF runs alongside ordinary traffic. Unwatched OSPF frames animate on a separate visual layer alongside user traffic, including during initial discovery and database synchronization. These animations do not delay other exchanges; Activity retains their protocol events. User traffic can start before convergence, but may fail until the required route is learned. Watch routing decisions pauses on OSPF exchanges, including routine Hellos and acknowledgments, as well as route changes. Turn routing Watch off to let these exchanges continue without examination pauses. Activity accepts ospf and ospf and not Hello; filters change visibility only. Select an event to see its recorded route state before and after, without rewinding the network.

Fail and repair a link

  1. Wait for Full neighbors and verify a ping.
  2. Disable a router-to-router cable. Local failure detection updates link state; silent neighbor loss is detected by the dead timer.
  3. Follow advertisements and route changes in Activity. Retry a ping after convergence. A remaining path is used; an isolated destination stays unreachable.
  4. Restore the cable. Adjacencies reform and the lowest-cost route returns.

For a one-fault exercise, load the discovery example and change Router B's transit interface to Passive. Hint: compare participation on both ends. Restore Active, wait for Full, and retry. Reload the example for a clean restart.

Save/load preserves configuration and static routes; OSPF relearns its database. Clear learned state also restarts discovery. Older networks have OSPF disabled. Link and router-interface changes preserve the rest of the simulation so recovery can be observed.

Model boundaries: IPv4, area 0, point-to-point router links and passive LANs. No shared transit LANs, DR/BDR elections, multiple areas, redistribution, authentication, or equal-cost load balancing. Database exchange uses the five OSPF message families but simplifies negotiation and packet encoding. Sequence numbers, aging, acknowledgments and retries are modeled; wire-level checksums, fragmentation and sequence-number rollover are not. LSA refresh/expiry are 1800/3600 simulation ticks. OSPF is IP protocol 89, not TCP or UDP.
